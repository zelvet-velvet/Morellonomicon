## 🧭 What this is

**Morellonomicon (黑魔禁書)** is a League of Legends guide for beginners, written in **Traditional Chinese (zh_TW)** as an Obsidian vault that opens on a phone. It covers roles, skill damage types, item-pick strategy per mode (Normal, Ranked, ARAM) and above all **ARAM Mayhem (大混戰)**: which augments fit which champion, and strong combos.

Base pages (champions, skills, items) are generated by Python scripts from public data; the advice (builds, augment fit, combos) is written and reviewed by people. Scripts use the **Python 3 standard library only**.

## ⚠️ Rules that prevent breakage

- **Language.** Vault content for readers is Traditional Chinese (Taiwan wording; use the official zh_TW client names for champions, items and augments). Workflow notes (this guide, Dev Status, Dev Log, CONTRIBUTING) stay English.
- **Generated vs written.** Generated pages carry `generated: true` in the frontmatter and a marked block; scripts only rewrite inside the marked block, never the hand-written advice around it.
- **Data sources are public and cited.** Riot Data Dragon (`ddragon.leagueoflegends.com`, `zh_TW`) and CommunityDragon. Every page shows the **patch version** it was generated from. Never invent statistics: win rates and pick rates come from a named source with a date, or are left out.
- **Riot policy.** Do not commit a Riot API key. Keys go in an environment variable (`RIOT_API_KEY`) or an untracked `.env`. Include Riot's legal line in the README ("not endorsed by Riot Games"). Do not copy another site's tier lists wholesale; link to them.
- **No dependencies.** Python standard library only; no pip installs.
- **Network use.** Only the fetch scripts touch the network, only to the public endpoints above, and only when the user runs them.
- **Nothing private in the repo.** No keys, personal paths or summoner names/IDs of real players.
- **Plugins are not in git** (`.obsidian/plugins/` is ignored). `tools/install_plugins.py` downloads them from each plugin's GitHub release; the list is `community-plugins.json`.
- **Visual changes** (CSS snippets, theme) start with a rendered picture or screenshot that Zaviel picks.
- **Testing needs the user's eyes** for Obsidian on a phone and on PC. Say what could not be tested and what the user must look at.

## 🔁 Workflow

1. Read [[Dev Status]] and the notes or script you are about to change before editing.
2. Make the smallest change that does the job; match the surrounding style.
3. Check it (run the script, open the generated note, read the Chinese text) and say plainly what works, what could not be tested and what you were unsure about.
4. Record it (see the commands below).
5. **Commit and push every change** on a feature branch, following the regulation below.

## 🌿 Regulation: repo management

The repo is on GitHub (`zelvet-velvet/Morellonomicon`). **Zaviel** (owner, `zelvet-velvet`) merges; everyone else is a contributor. The human version is `CONTRIBUTING.md`.

**Branches**
- `main` is the stable line. Nobody commits or pushes to it directly; it only receives pull requests. (Only the very first commit that created the repo went straight to `main`.)
- Work on a branch off a fresh `main`, named `type/short-slug`, for example `feat/aram-mayhem-augments`, `fix/zh-tw-item-names`. One topic per branch.

**Commit messages:** `type(scope): summary`, lowercase, imperative, no trailing period.
- `type` is one of `feat`, `fix`, `refactor`, `chore`, `docs`.
- `scope` is the area touched: `champions`, `augments`, `modes`, `tools`, `vault`, `css`, `docs`...
- Example: `feat(augments): add the augment list for patch 16.21`.
- End each commit message with the co-author line from the session's attribution rules. Pull request descriptions end with the attribution line from the session's rules.
- Git identity: the user's own, set in the repo (not globally). Check `git config user.name` to know whom you work with. Use the GitHub no-reply address, not a private email.

**Every change = commit + push** on the current feature branch, without asking; never force-push a shared branch or `main`.

**Pull requests and merging**
- When a feature is done, **open a pull request** into `main` with `gh pr create` (the template asks what changed, pictures, what was checked). Before that, `git fetch && git merge origin/main`.
- **Only Zaviel merges** ("Create a merge commit"). You may merge a PR when Zaviel says in the conversation that they checked it and it is ready (`gh pr merge N --merge`, then delete the branch). Never merge on your own judgement, and never someone else's PR unless Zaviel says so.
- After a merge, delete the branch (GitHub's button, then `git branch -d` locally).

## 📜 Commands: status, journal

The progress lives in two places: **[[Dev Status]]** (`Review/Dev Status.md`: 🚀 Today (date), 📅 Yesterday (date), ⏳ Ongoing by area, 💡 Ideas, 🏁 Last Progress) and the **day notes** (`Review/Log/YYYY/MM/Www/YYYY-MM-DD.md`, one `## ` entry per change; the [[Dev Log]] lists them). **Read before edit**: always read the note right before changing it; the user may have rolled something back: never put it back.

- **CMD_SYNC**: From the chat and `git log` / `git status`, update Dev Status: `Today`, `Yesterday` and `Ongoing` (`[x]` done, `[>]` in progress, `[ ]` not started; by area). Keep the `Today` heading date right: an earlier date with items → `CMD_ROLLOVER` first (or ask); empty → just set today. **Results, not steps**: one line per item, bold title, no file lists (details belong in the notes: link them).
- **CMD_JOURNAL [YYYY-MM-DD]** (default today): Write that day's note from `Today's Progress` (or `Yesterday's` when its date matches). Make the note from [[Day note]] if it is missing (outside Obsidian: copy the last day's frontmatter, make the year / month / week folders). One `## ` entry per change, newest first: an emoji title with the author in brackets, two to four plain bullets of what changed **for the reader of the vault**, the branch if not merged, pictures if visual. Then add the day to the [[Dev Log]] list.
- **CMD_ROLLOVER**: The day is over. If the day note has no entries for `Today`'s items, run `CMD_JOURNAL` for that date first. Then replace `Yesterday` with `Today`'s list and date, clear `Today` and set its heading to today. `Today` empty → change nothing and say to run `CMD_SYNC` first (never overwrite `Yesterday` with an empty list).
- **CMD_NOTES_SYNC**: Bring the notes up to date, then retire finished work: update `README.md` / `CONTRIBUTING.md` / this guide if a rule or command changed; move `[x]` items from `Ongoing` to `Last Progress` (one line each, by area, result only). Leave `[>]` and `[ ]`.
- **Trust order** (when sources disagree): the code, then today's chat and Dev Status, then other notes. If a note contradicts the code, say so and suggest `CMD_NOTES_SYNC`.
- **Commit**: vault updates go on their own branch as `docs(vault): sync` (or the command's name), with a pull request.
- **Notifications**: at the very end, only for what changed, one line each: `**[Today's Progress]** Updated in Dev Status`, `**[Journal]** 2 entries in 2026-10-27`. A blank line before and after.

## 🗣️ Conventions

- Call the user by the name in `git config user.name`. Reply in the language they write in.
- **Notes:** no `# Title` heading inside a note (Obsidian shows the file name as its title); give workflow notes a `sticker:` lucide icon in the frontmatter. Never write a note named like its folder (make.md's folder notes).
- Champion, item and augment names are linked with `[[ ]]` so the graph and backlinks work (champion ↔ augment ↔ combo).
- Prefer a named constant at the top of a script over a magic number.
